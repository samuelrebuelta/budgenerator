# BG-014 — Informe de los spikes de fase 0

Spikes de la fase 0 de la [spec BG-014](../BG-014-app-nativa.md), ejecutados el 14-11-2026 en el dev client (`APP_VARIANT=development`) contra emuladores de Firebase `demo-budgenerator` (Auth 9199, Firestore 8180; nunca producción). Registro de la ejecución: [paso 4](2026-11-14-bg-014-ejecucion.md#paso-4--spikes). Sólo resultados ejecutados.

| Spike                                             | Decisión                                                             | Dato que la apoya                                                                                                         |
| ------------------------------------------------- | -------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------- |
| D2 · repositorio `project` con RNFB               | **Go**: repositorios compartidos con el SDK inyectado                | El mismo `createProjectRepository` pasa 22/22 pasos en iOS con RNFB y las pruebas de reglas y E2E de la web con el SDK JS |
| PDF en Hermes                                     | **Go**: `buildBudgetDocument` (jsPDF) en el móvil; sin `expo-print`  | PDF de 13 páginas byte a byte igual al de Node (SHA-256 sin `CreationDate`/`ID`); 50 ms en iOS, 396 ms en Android         |
| D3 · borrado de persistencia al cambiar de cuenta | **Go**: `resetSession` en `apps/mobile/src/platform/sessionReset.ts` | Sin reset, B lee de la caché 1 documento de A; con reset, 0 documentos y MMKV de A inexistente                            |
| Push en dispositivo físico                        | **Pendiente**                                                        | Requiere la licencia de Apple Developer (y dispositivos físicos): no se ha ejecutado                                      |
| Globales de Hermes                                | **Go con una corrección pendiente**                                  | Todas las APIs presentes; `Intl` de Android agrupa `1.234,50` donde Node/iOS dan `1234,50`                                |

## Entorno

- Mac con Xcode 27.2. Simulador iPhone 17 Pro (iOS 26.5) y emulador Android Pixel 9 Pro (ya arrancado y compartido con otro proyecto; sin DNS hacia Internet).
- Expo SDK 58.0.25, React Native 0.88.1, Hermes, `@react-native-firebase/*` 27.1.1, `jspdf` 4.2.1.
- Emuladores: `pnpm exec firebase emulators:start --project demo-budgenerator --only auth,firestore` con los puertos por defecto de `firebase.json` (estaban libres).
- Código de los spikes: `apps/mobile/src/dev/spikes/*` y la ruta `app/dev/spikes.tsx` (sólo `development`). Se lanzan con `budgenerator://dev/spikes?run=d2|pdf|d3|persist-write|persist-probe&n=<nonce>`; cada uno escribe `[spike] …` en Metro y un JSON en `Documents/spikes/`. Las salidas y capturas quedaron fuera del repositorio.
- La siembra usa la API REST del emulador con el token `owner` (`src/dev/emulatorAdmin.ts`, como `withSecurityRulesDisabled` en las pruebas de reglas) y rechaza ejecutarse fuera de `development` o contra un proyecto que no sea `demo-*`. Todas las operaciones del repositorio pasan por las reglas reales del emulador.

## D2 — Repositorio `project` con React Native Firebase

**Método.** Se movió `createProjectFirestoreApi` de `src/entities/project/api/firestore.ts` a `packages/firebase-api/src/project.ts` como `createProjectRepository({ sdk, database, guardMutation })`, sin cambiar su cuerpo: las funciones del SDK se desestructuran del puerto al principio de la factoría. La web conserva `createProjectFirestoreApi(db)` como enlace de una línea con `webFirestoreSdk` y `guardNetworkMutation`; el móvil inyecta `nativeFirestoreSdk`. En el simulador, el spike crea un usuario sintético en el emulador de Auth, siembra un presupuesto aceptado (2 capítulos, 3 partidas) y una persona del equipo y ejecuta las operaciones del repositorio.

**Puerto mínimo** (`packages/firebase-api/src/firestorePort.ts`): `collection`, `doc`, `getDoc`, `getDocFromServer`, `getDocs`, `getDocsFromServer`, `setDoc`, `updateDoc`, `deleteDoc`, `deleteField`, `query`, `where` y `runTransaction`, más el tipo `MutationGuard`. Los tipos son estructurales (`DocumentReferenceLike`, `DocumentSnapshotLike` con `exists(): this is …`, `TransactionLike`…) y los miembros usan sintaxis de método para que TypeScript acepte las sobrecargas genéricas de ambos SDK. Comprobado con `tsc`: los dos objetos SDK compilan contra el puerto sin casts, y un cruce deliberado (`getDoc` ↔ `getDocs`, `Timestamp` donde va `string`) sí falla.

**Diferencias encontradas**

| Área                     | Resultado                                                                                                                                                                                                                                                                        |
| ------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `doc(docRef, 'sub', id)` | **Bug de RNFB 27**: está tipado como en la web pero se implementa como `parent.doc(path)`, que un `DocumentReference` no tiene (`TypeError: undefined is not a function` en `readStoredDocument`). El adaptador nativo resuelve esas rutas desde la raíz (`firestore` + `path`). |
| `Timestamp`/`FieldValue` | Clases distintas en cada SDK. No afectan: el repositorio guarda fechas ISO y sólo devuelve `deleteField()` al SDK como valor opaco.                                                                                                                                              |
| Transacciones            | Misma API (`get`/`set`/`update`/`delete`, reintentos) y mismo resultado, incluido `Promise.all` de lecturas dentro de la transacción.                                                                                                                                            |
| Queries                  | `query` + `where('date', 'in', …)` funcionan igual.                                                                                                                                                                                                                              |
| `getDocFromServer`       | Existe en la API modular de RNFB y se comporta igual.                                                                                                                                                                                                                            |
| `signOut` sin usuario    | RNFB lo rechaza (`auth/no-current-user`); el SDK web no. `resetSession` lo comprueba antes.                                                                                                                                                                                      |

**Resultado medido** (iOS, segunda ejecución; la primera paró en el bug de `doc`):

| ------------------------------------------------------------------------------------------- | ------------------ | ------------------------------------------------ |
| `convertBudgetToProject` (transacción)                                                      | 85,5               | proyecto creado, revisión del presupuesto 2      |

Del lado web, el mismo código pasa `pnpm test:rules` (incluye `projectConversion`, `projectAssignments`, `projectDailyAssignments`, `projectSupplement`… que usan `createProjectFirestoreApi`) y `pnpm test:e2e` (resultados en el registro).

En **Android** no se pudo ejecutar: `createUserWithEmailAndPassword` falla tras 10 s con `auth/network-request-failed` aunque el emulador de Auth responde desde el dispositivo (`nc` y una petición HTTP a `10.0.2.2:9199` dan 200). El emulador Android compartido no resuelve DNS de Internet; la hipótesis es que el SDK de Auth de Android intenta una llamada no emulada antes del alta. No se modificó ese emulador (es de otro proyecto). Queda como TODO.

**Decisión: go.** Las diferencias reales son dos detalles del adaptador nativo (`doc` sobre un `DocumentReference` y `signOut` sin usuario), resueltos en `apps/mobile/src/platform`, no en el repositorio. Un único código de repositorio evita una segunda implementación de transacciones con reglas delicadas (conversión, asignaciones con revisión, suplementos). La suite de contrato común sigue siendo útil, pero como prueba del puerto, no como sustituto. Siguiente paso (fase 1): mover el resto de repositorios a `@bg/firebase-api` con el mismo patrón y añadir al puerto lo que pidan (`writeBatch`, `onSnapshot`, `httpsCallable` con región).

## PDF en Hermes

**Método.** `longBudgetPdfInput()` (`packages/domain/tests/pdfFixtures.ts`, nuevo y usado también por `tests/pdf.test.ts`) da el mismo documento largo (32 partidas con descripción extensa) en Node y en la app. En el dispositivo: una generación en frío, una medida, cinco repeticiones (mediana), escritura con `expo-file-system` (`File.write`) y SHA-256 con `expo-crypto` tras quitar `/CreationDate (D:…)` y `/ID [<…> <…>]` (`stripVolatile` en `src/dev/spikes/pdf.ts`). La referencia de Node es la salida de `CIMBRA_PDF_QA=1 vitest run packages/domain/tests/pdf.test.ts`, normalizada con las mismas expresiones.

**Resultado**

| Motor            | Páginas | Bytes  | Frío   | Mediana ×5 (mín–máx) | Escritura | SHA-256 normalizado |
| ---------------- | ------- | ------ | ------ | -------------------- | --------- | ------------------- |
| Node 24 (Vitest) | 13      | 83 928 | —      | —                    | —         | `8c6ba69c…ee3462b5` |
| Hermes iOS 26.5  | 13      | 83 928 | 66 ms  | 50 ms (50–62)        | 9,8 ms    | `8c6ba69c…ee3462b5` |
| Hermes Android   | 13      | 83 928 | 599 ms | 396 ms (385–434)     | 38,3 ms   | `8c6ba69c…ee3462b5` |

Los tres ficheros son idénticos salvo fecha e ID. Android es un emulador sobre el Mac, no un teléfono: la cifra es una cota alta. El hash difiere del `013bb37e…` del paso 1 porque allí se normalizó de otra forma; la comparación válida es la de esta tabla, con la misma normalización.

**Compartir.** `Sharing.shareAsync(uri, { mimeType: 'application/pdf', UTI: 'com.adobe.pdf' })` abre la hoja nativa de iOS con la vista previa «long-budget · Documento PDF · 84 KB» y las acciones Vista Previa, Copiar, Markup e Imprimir.

**Limitación detectada (ver globales).** El documento de prueba no tiene importes entre 1.000 y 9.999 €, así que no cubre la agrupación de miles. En Android, `toLocaleString('es-ES')` agrupa `1.234,50` donde Node, la web e iOS dan `1234,50`: un PDF con esos importes no sería idéntico en Android hasta corregir el formato.

**Decisión: go** con jsPDF. No hace falta `expo-print` ni sacar jsPDF a un subpaquete. Pendiente para la fase 1: logo (leer ancho y alto de la cabecera PNG en vez de `Image`/canvas), el test de paridad con importes ≥ 1.000 € y medir en un Android físico de gama media.

## D3 — Borrado de persistencia al cambiar de cuenta

**Implementación reutilizable**

- `apps/mobile/src/platform/userStorage.ts`: un MMKV por UID (`user.<uid>`); `deleteUserStorage(uid)` hace `clearAll` y `deleteMMKV`.
- `apps/mobile/src/platform/sessionReset.ts`: `resetSession(uid, port?)` ejecuta `terminate` → `clearPersistence` → reconectar el emulador (sólo `development`) → borrar MMKV del UID → `signOut` (sólo si hay usuario). Ejecuta todos los pasos aunque falle uno, no intenta `clearPersistence` si `terminate` falló y lanza `SessionResetError` con los pasos fallidos. Las operaciones nativas están detrás de `SessionResetPort` para poder probarlo.
- Hallazgo del código nativo de RNFB 27: `terminate` elimina la instancia nativa y su vínculo con el emulador; la siguiente llamada crea otra **sin emulador**. Por eso `resetSession` vuelve a llamar a `connectFirestoreToEmulator()` (`firebase.ts`), que es un no-op fuera de `development`.

**Prueba manual real (iOS)**, persistencia en disco nativa por defecto:

| Paso                                                                                     | Resultado                                                                                                 |
| ---------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------- |
| Control: A lee sus presupuestos del servidor y cierra sesión sólo con `signOut`; entra B | B lee con `getDocsFromCache` **1 documento de A** (la fuga que D3 evita; la caché no pasa por las reglas) |
| A lee (servidor → caché: 1 documento), guarda `lastTab` en su MMKV                       | OK                                                                                                        |
| `resetSession(A)`                                                                        | 3,1 ms; `existsMMKV('user.A') = false`                                                                    |
| B inicia sesión: `getDocsFromCache(users/A/budgets)` y `getDocFromCache` de la raíz      | 0 documentos; la raíz no está en caché (`firestore/unavailable`)                                          |
| B lee del servidor tras el reset                                                         | OK, `fromCache=false` (el emulador vuelve a estar conectado)                                              |
| Persistencia entre arranques: A lee, se mata la app y se relanza; `getDocsFromCache`     | 1 documento de A en disco                                                                                 |
| Tras ese arranque, `resetSession(A)` y `getDocsFromCache`                                | 0 documentos                                                                                              |

**Test automatizado** (`apps/mobile/tests/sessionReset.test.ts`, Jest): con mocks de RNFB que modelan la caché (y fallan `clearPersistence` sin `terminate`, como el SDK nativo) comprueba el orden, que la caché y el MMKV de A quedan vacíos, que el MMKV de otra cuenta no se toca, que no se llama a `signOut` sin usuario y el comportamiento ante fallos. `react-native-mmkv` usa su mock en memoria bajo Jest; `tests/setup.ts` sólo simula el cargador de Nitro.

**Decisión: go.** Riesgo anotado: `clearPersistence` descarta escrituras pendientes. Hoy no las hay (D4 bloquea las mutaciones sin red), pero la fase 3 (marcar partidas sin red) tendrá que vaciarlas o avisar antes de cerrar sesión. En fase 1, `@bg/app-core` añade antes los pasos de `prepareSignOut` (dispositivo push, token FCM, `WriteQueue`) y bloquea el siguiente inicio de sesión si `resetSession` lanza.

## Globales de Hermes

Comprobado en el diagnóstico del login (`runtimeSelfCheck`, iOS y Android) y en uso real por los spikes:

| API                                                  | iOS               | Android            | Uso                                        |
| ---------------------------------------------------- | ----------------- | ------------------ | ------------------------------------------ |
| `structuredClone`                                    | ✓                 | ✓                  | modelo BC3                                 |
| `TextEncoder` / `TextDecoder` (UTF-8)                | ✓                 | ✓                  | límite de tamaño de `saveDailyAssignments` |
| `URL` / `URLSearchParams`                            | ✓                 | ✓                  | enlaces de avisos                          |
| `Intl` (`es-ES`, `PluralRules` con polyfill)         | ✓                 | ✓                  | importes, `t()`                            |
| Agrupación de miles `es-ES` (`1234,50 \| 12.345,50`) | ✓                 | **✗** (`1.234,50`) | PDF y textos de importes                   |
| `atob` / `btoa`                                      | ✓                 | ✓                  | jsPDF                                      |
| `crypto.randomUUID`                                  | ✗ (`expo-crypto`) | ✗ (`expo-crypto`)  | `generateId`                               |
| `performance.now`                                    | ✓                 | ✓                  | medidas de los spikes                      |

No hacen falta más polyfills para lo probado. La agrupación queda como TODO de fase 1: formatear en `@bg/domain` sin depender de la agrupación de `Intl` del motor (o con un formateador propio que reproduzca la de ICU), con un test de paridad.

## Push en dispositivo físico

No ejecutado: necesita la licencia de Apple Developer (entitlement de push, firma de dispositivo) y dispositivos iOS y Android físicos con una cuenta sintética contra `budgenerator` (D5). Queda como TODO de la fase 0.
